DDIC objects for ZCR_GET_OBJECT_SIGNATURE
===========================================================================
STATUS: created in the system. Actual field/type names below reflect what
was actually built (DEFAULT is an ABAP reserved word, so that field is
named ZDEFAULT instead; ABAP_BOOL was substituted with FLAG - both are
CHAR1 domains with 'X'/' ' values, so no code impact either way).

1) Structure ZCR_TS_SIG_PARAM  ("one parameter of a signature")
   Short text: Signature Parameter (Code Extractor)

   Component   Typing Method   Component Type
   ---------   -------------   --------------
   NAME        Types           Z_STRING   " STRING, via data element
   KIND        Types           Z_STRING   " IMPORTING / EXPORTING / CHANGING / TABLES / RETURNING
   TYPE        Types           Z_STRING   " resolved ABAP type name, e.g. STRING, BAPIRET2, ZCL_FOO
   OPTIONAL    Types           FLAG
   ZDEFAULT    Types           Z_STRING   " only populated for IMPORTING/CHANGING kinds ("DEFAULT" is reserved)

2) Table type ZCR_TT_SIG_PARAM
   Short text: Signature Parameter Table (Code Extractor)
   Line type: ZCR_TS_SIG_PARAM
   Kind: Standard Table
   (No key needed - default/standard key is fine, code only uses APPEND/LOOP.)

3) Structure ZCR_TS_SIGNATURE  ("enrichment attached to one dependency")
   Short text: Dependency Signature (Code Extractor)

   Component      Typing Method   Component Type
   ---------      -------------   --------------
   PROGRAM_TYPE   Types           Z_STRING        " PROG/INCL only: Executable/Include/Function Group/etc.
   IS_INCLUDE     Types           FLAG            " PROG/INCL only
   PACKAGE        Types           DEVCLASS        " PROG/INCL only
   VISIBILITY     Types           Z_STRING        " METH (class) only: PUBLIC/PROTECTED/PRIVATE
   IS_STATIC      Types           FLAG            " METH only
   PARAMETERS     Types           ZCR_TT_SIG_PARAM   " FUNC / METH
   EXCEPTIONS     Types           STRING_TABLE    " FUNC / METH (STRING_TABLE already exists in SAP standard)

DDIC objects for ZCR_SCAN_CODE_SIGNALS (code_signals feature)
===========================================================================
STATUS: created in the system. COUNT and LEVEL both turned out to be
reserved words, so those fields are ZCOUNT and ZLEVEL. The JSON keys still
have to read "count" and "level", so ZCR_GET_DEPENDENCY_OBJ_NEW passes a
NAME_MAPPINGS table on its /ui2/cl_json=>serialize call to map them back.

4) Structure ZCR_TS_CODE_SIGNAL  ("one risky construct found in a dependency")
   Short text: Code Signal (Code Extractor)

   Component   Typing Method   Component Type
   ---------   -------------   --------------
   TYPE        Types           Z_STRING   " db_select / commit_work / rfc_call / ...
   DETAIL      Types           Z_STRING   " e.g. "SELECT SINGLE on table VBAP"
   ZCOUNT      Types           INT4       " repeats of same TYPE+DETAIL collapsed into one row
   ZLEVEL      Types           INT4       " 1 = in the dependency itself, 2 = in something it calls
   VIA         Types           Z_STRING   " only filled when ZLEVEL > 1

5) Table type ZCR_TT_CODE_SIGNAL
   Short text: Code Signal Table (Code Extractor)
   Line type: ZCR_TS_CODE_SIGNAL
   Kind: Standard Table

6) Structure ZCR_TS_DEP_REF  ("one discovered callee, no enrichment")
   Short text: Dependency Reference (Code Extractor)

   Component     Typing Method   Component Type
   ---------     -------------   --------------
   TYPE          Types           Z_STRING
   NAME          Types           Z_STRING
   LOOKUP_NAME   Types           Z_STRING
   ENRICH_TYPE   Types           Z_STRING
   PARENT        Types           Z_STRING

   Mirrors the TY_CANDIDATE type local to ZCR_GET_DEPENDENCY_OBJ_NEW. It exists
   as a DDIC type only because a function module interface cannot be typed with
   a type local to another program.

7) Table type ZCR_TT_DEP_REF
   Short text: Dependency Reference Table (Code Extractor)
   Line type: ZCR_TS_DEP_REF
   Kind: Standard Table

Notes:
- No DESCRIPTION field, per decision to drop short-text enrichment for all types
  (not cheaply retrievable for CLAS/INTF methods, dropped everywhere for consistency).
- ZCR_GET_OBJECT_SIGNATURE.txt has been updated to assign ZDEFAULT (not DEFAULT)
  when building ZCR_TS_SIG_PARAM rows.
- Fields irrelevant to a given dependency's type are left blank by
  ZCR_GET_OBJECT_SIGNATURE. The calling FM (ZCR_GET_DEPENDENCY_OBJ) serializes
  with /ui2/cl_json=>serialize( compress = abap_true ), which drops blank/initial
  fields from the JSON output, so each dependency's JSON only shows relevant keys.

DDIC objects for ZCR_AI_CODE_REVIEW / ZCR_AI_REVIEW_CHUNK (direct-API AI review, branch DIRECT-API-CODE-REVIEW)
===========================================================================
STATUS: not yet created - needed before these two FMs will activate.

8) Structure ZCR_TS_AI_FINDING  ("one code review finding")
   Short text: AI Code Review Finding (Code Extractor)

   Component      Typing Method   Component Type
   ---------      -------------   --------------
   RULE_FILE      Types           Z_STRING   " which rule CSV the finding came from
   RULE_SERIAL    Types           Z_STRING   " S.No. column in that CSV
   RULE_HEADING   Types           Z_STRING   " Rule column
   RULE_TAG       Types           Z_STRING   " MUST / MUST NOT / SHOULD / SHOULD NOT, as given by the rule
   OBJECT_NAME    Types           Z_STRING   " set by ZCR_AI_CODE_REVIEW, not trusted from the model
   LINE_NOS       Types           Z_STRING   " e.g. "42" or "42-47" or "42, 58"
   REMARKS        Types           Z_STRING   " violation explanation
   FIX            Types           Z_STRING   " recommended fix
   REVIEW_CHUNK   Types           Z_STRING   " "Chunk N" - set by ZCR_AI_CODE_REVIEW, not the model

9) Table type ZCR_TT_AI_FINDING
   Short text: AI Code Review Finding Table (Code Extractor)
   Line type: ZCR_TS_AI_FINDING
   Kind: Standard Table
   (No key needed - APPEND/LOOP/MODIFY ... INDEX only, same as ZCR_TT_DEP_REF.)

Notes:
- The model is asked for 8 JSON keys (ruleFile, ruleSerial, ruleHeading, ruleTag,
  objectName, lineNos, remarks, fix) via /ui2/cl_json=>deserialize( pretty_name =
  camel_case ) into ZCR_TT_AI_FINDING directly. OBJECT_NAME and REVIEW_CHUNK are
  then overwritten in ABAP regardless of what the model returned, since those two
  are known authoritatively by the caller.
- The TSV output (ZCR_AI_CODE_REVIEW, section 5) has 4 more columns than this
  structure - Remediation Status, Developer Comments, Target Completion Date,
  Reviewer Sign-Off - left blank for manual entry later. They're written straight
  into the TSV, not modeled as DDIC fields, since nothing ever populates them
  programmatically.
